# GitHub Copilot Instructions — Shotput Blender Add-on

## 🎬 Project Context
This repository contains **Shotput**, a comprehensive Blender add-on for managing file output nodes with:
- Advanced token-based path resolution
- Smart format overrides
- Automated version management
- Node path linking across composite hierarchies

Shotput operates inside Blender’s **Compositor and Render Output node systems** and is designed for **professional VFX and animation pipelines**.  
All suggestions from Copilot should assume:
- The add-on runs in **Blender’s Python environment** (`bpy` context)
- It must maintain **compatibility with Blender 3.x and 4.x**
- It integrates cleanly with production file structures and naming conventions

---

## 🧠 Code Conventions
- Follow **PEP8**, 4-space indentation.
- Keep **registration** and **UI class declarations** organized by domain:
  - `/core/` for logic (token parsing, versioning, linking)
  - `/ui/` for Panels, Menus, Operators
  - `/utils/` for shared functions and helpers
- Maintain clean separation between **token logic**, **format logic**, and **UI rendering**.

### Naming
- Operators: `class SHOTPUT_OT_OperatorName`
- Panels: `class SHOTPUT_PT_PanelName`
- PropertyGroups: `class SHOTPUT_PG_...`
- Functions: lowercase with underscores
- Tokens: always wrapped in `{}` syntax and lowercase (e.g. `{frame}`, `{project}`)

---

## 🏷️ Token Parsing System
When modifying or extending token handling:
- Use the `TokenParser` class as the single source of truth.
- Add new tokens by extending the internal mapping dictionary.
- Each token should include:
  - A **short description**
  - A **context-safe resolution method** (scene, render layer, etc.)
  - **Preview-safe fallback behavior** for unregistered contexts
- Avoid hardcoding absolute paths; use Blender scene or project data.

If Copilot suggests code:
- Prefer modular functions like `resolve_token_path()` or `preview_resolved_path()`.
- Never suggest reading or writing outside the Blender project directory.

---

## 🎨 File Format Override System
Copilot should respect the rules:
- Core & AOV passes → use **UI-selected format**
- Data passes → force **OPEN_EXR_MULTILAYER (32-bit)**
- Prefer clean conditional handling (`if pass_type == "DATA": ...`) rather than multiple format branches.
- Always ensure file extension matches the format (`.exr`, `.png`, etc.)

If suggesting improvements, focus on:
- Simplifying branching logic
- Improving clarity between **user choice** vs **forced rule**

---

## 📁 Version Management
Versioning logic must:
- Avoid side effects during path preview
- Only increment versions with explicit user confirmation
- Respect existing versioning systems (e.g., AYON)
- Handle version strings consistently: `v001`, `v002`, etc.

Copilot should not suggest code that automatically creates directories during previews.

---

## 🔗 Path Linking System
When dealing with node path linking:
- Parent nodes define the base path; child nodes inherit it dynamically.
- Preserve original token strings for reversibility.
- Ensure linking state toggles cleanly (`enabled` / `disabled`).
- Provide user feedback in the UI (status labels, icon updates).

When proposing refactors:
- Maintain the real-time update behavior in the node UI.
- Avoid recursive updates or excessive context polling.

---

## ⚙️ Pass Categories
- **Core Passes:** beauty, diffuse, specular, reflection  
  → serve as parent link sources  
- **AOV Passes:** AO, shadow, fresnel, roughness  
  → child nodes linked to core folder structures  
- **Data Passes:** z-depth, mist, normal, vector, crypto  
  → always EXR Multilayer, full precision

Copilot should avoid merging logic across these categories.

---

## 🔄 Improvements and Refactors
Copilot should prioritize:
1. **Code clarity** (readable and modular)
2. **Non-destructive refactors** (no behavioral changes unless intentional)
3. **Performance** (avoid unnecessary recomputation)
4. **Safety** (graceful handling when nodes or scenes are missing)

Do **not** suggest global refactors that alter token behavior, path construction rules, or versioning semantics without explicit user request.

---

## 🧾 Issue and PR Guidelines
When suggesting or responding to issues:
- Reference specific files and functions (e.g., `core/token_parser.py`).
- Describe **functional impact**, not just code differences.
- Suggest incremental changes and document expected behavior.
- For bug fixes, include sample test cases or reproduction steps (scene setup + node graph example).

Commit and PR naming:
- `Fix:` for bug fixes  
- `Add:` for new features or tokens  
- `Refactor:` for structural code improvements  
- `UI:` for interface or label updates  

---

## 🧪 Testing and Validation
- Always ensure `register()` and `unregister()` work without error in Blender scripting console.
- Avoid proposing solutions that rely on Blender UI context when running in headless mode (e.g. `bpy.app.background`).
- For new functionality, suggest inline test operators (e.g. `SHOTPUT_OT_test_*`) to validate results.

---

## 🧰 Documentation
- Keep `bl_info` accurate (name, version, category, author, description).
- Encourage docstrings for public functions and operator classes.
- Update README.md when UI layout, behavior, or requirements change.

---

## 🧩 Integration Context
Shotput integrates into VFX pipelines using **AYON**, **Deadline**, or similar DCC management systems.  
Copilot should treat any references to these as external integrations, not dependencies, and avoid proposing direct API calls unless pre-existing integration files handle them.
